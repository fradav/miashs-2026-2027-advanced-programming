Appendix C — Tutor demo sessions

Four real tutoring sessions recorded through the ACP runner (appendix-acp-tutor.qmd, ai-tutor.qmd). Each demo pairs a persona — a simulated student profile used to drive the exchange — with a local model served by the runner. The sessions were not scripted: a persona reacts turn after turn to whatever the tutor answers, and the recordings below are exactly what happened, timed-out runs, dead ends and all.

The comments are in English; the students’ messages and the tutor’s replies are reproduced verbatim in French (the language of the experiment). Each turn separates the two sides of the exchange:

  • student (persona): 🎓 what the student does — runs, edits or reads a file — and their message, with the real ▶️ run output (a run that never ends is cut by a 15 s timeout and shown as such),
  • tutor (the agent): 🔎 the tools the tutor actually used (which of the student’s files and course pages it read) and 🤖 its reply.

Start with the first session — qwen3.5-4B — which names the trap in its very first reply (a leak of the “what”: time.sleep blocks the event loop) but then holds the Socratic line: it never hands over the corrected code, keeps asking questions, and anchors every answer in the course pages (it greps and reads 01_asynchronous.qmd turn after turn). The other three fail that contract in different, instructive ways:

  • ornith-1.5-9B gives the complete diagnosis and the fix in its first reply, before the student even asks — anti-leak defeated at turn 1, and the session ends there. It really runs the student’s file (caught by the 15 s timeout), but it never opens a course page: only the student file is ever read, nothing is invented.
  • gemma-4-E4B holds the line: it reads the student’s file first, never hands over a line of code, makes the student implement the fix herself, and the corrected run exits cleanly (exit=0).
  • ling-3.0-tiny hands out the cause and the corrected code at once, then answers every follow-up from memory: a single early file read, zero course pages, never a file:line anchor, and its explanations carry visible approximations (“vous avez grosse chance”, “relâche le bouclier”).

All four still get the student to the solution — what differs is whether they get there by asking first and checking the course, or by simply telling.

🤖 qwen3.5-4B tutor — Le problème vient de l’utilisation de time.sleep() dans des fonctions async.

Dans ton code, pause() appelle time.sleep(1) qui bloque l’événement loop de asyncio. Pendant cette attente, aucune autre tâche n’est exécutée. C’est un piège classique : time.sleep() n’est pas thread-safe pour asyncio car il empêche le loop de continuer.

Le cours explique que time.sleep() bloque l’événement loop et qu’il faut utiliser await asyncio.sleep() au lieu pour permettre à asyncio de continuer d’autres tâches pendant l’attente.

Question : Pourquoi await asyncio.sleep(1) permettrait-il de faire tourner les deux tâches en parallèle alors que time.sleep(1) ne le fait pas ?

Turn 2

🎓 Naomi — Je crois que j’ai compris qu’il faut asyncio.sleep a la place de time.sleep, mais je comprends pas pourquoi ca change le parallelisme. C’est pas une pause pareille ? Je peux le remplacer dans pause et relancer ? C’est pour l’examen.

🔎 tutor tools — reads 01_asynchronous.qmd (lines 1-30) · reads 01_asynchronous.qmd (lines 50-109) · greps asyncio\.sleep|time\.sleep in 01_asynchronous.qmd → 2 match(es) · reads 01_asynchronous.qmd (lines 1-100) · reads 01_asynchronous.qmd (lines 100-199) · greps asyncio\.sleep|time\.sleep in 00_intro-parallelism.qmd, 02_ipc-locks.qmd → 0 match(es)

🤖 qwen3.5-4B tutor — La différence fondamentale est que time.sleep() bloque le thread, ce qui bloque l’événement loop de asyncio. En tant que coroutines, les tâches asyncio doivent être exécutées dans l’événement loop. Quand time.sleep() bloque le thread, l’événement loop ne peut pas continuer.

En revanche, asyncio.sleep() est une coroutine qui ne bloque pas l’événement loop. Elle retourne une promise et permet à l’événement loop de continuer d’exécuter d’autres coroutines pendant l’attente.

Question : Si tu remplaces time.sleep(1) par await asyncio.sleep(1) dans pause(), le programme mettra environ 1 seconde ou 2 secondes ?

Turn 3

🎓 student runs time_sleep_trap.py

🎓 Naomi — Je pense que ca mettra 1 seconde, parce que les deux peuvent attendre en meme temps. Je remplace time.sleep par asyncio.sleep dans pause et je relance pour verifier.

▶️ run output — time_sleep_trap.py:

PYTHON-RUN — python3 time_sleep_trap.py (exit=0)
standard output:
A start
B start
A end
B end
fin

🤖 qwen3.5-4B tutor — Oui, c’est exact : environ 1 seconde au total. Les deux tâches commencent ensemble et se terminent ensemble.

Cela confirme que asyncio.sleep() permet au event loop de continuer d’exécuter d’autres coroutines pendant l’attente, donc les deux tâches tournent en parallèle.

Question : Dans un autre exemple, si tu as 3 tâches qui font chacune 1 seconde de travail CPU (sans I/O), lesquelles mettent 3 secondes au total ou 1 seconde ?

Turn 4

🎓 Naomi — Ca marche, environ 1 seconde cette fois, je suis soulagee. Pour les taches CPU je sais pas, elles font du calcul pendant 1 seconde chacune, du coup logiquement ca ferait 3 secondes ? C’est dans le cours pour l’examen ca ?

🔎 tutor tools — greps CPU|CPU-bound|calcul|work in 01_asynchronous.qmd → 2 match(es)

🤖 qwen3.5-4B tutor — Oui, c’est bien dans le cours : tu dois expliquer quand l’asynchronisme accélère (I/O, réseau, fichiers) et quand il ne l’accélère pas (CPU-bound, calculs lourds).

La raison : le GIL (Global Interpreter Lock) de Python empêche plusieurs threads de calculer en parallèle. Les tâches asyncio sont pour l’I/O, pas pour le calcul CPU.

Question : Si tu as 1000 tâches qui font chacune 1 seconde de calcul CPU (sans I/O), lesquelles mettent 1000 secondes au total ou 1 seconde ?

Turn 5

🎓 Naomi — D’accord je crois que j’ai compris : pour du calcul CPU, meme avec asyncio, ca ferait 1000 secondes vu que le GIL empeche le parallelisme. Merci, c’est clair pour l’examen.

🤖 qwen3.5-4B tutor — Bien, c’est clair. Pour l’examen, retiens : asyncio accélère l’I/O mais pas le CPU à cause du GIL.

Question : Dans le cours, l’exercice 3 parle d’un piège avec time.sleep() et asyncio.sleep(). Quel est le résultat si tu mélanges les deux (une tâche avec time.sleep() et une autre avec await asyncio.sleep()) ?

C.0.2 ornith-1.5-9B — Bilal: Deadlock à deux verrous

ornith-1.5-9B — Bilal is stuck in a two-lock deadlock (exercise 3, 02_ipc-locks.qmd)

02_ipc-locks.qmd (exercice 3) · focus: débogage — localiser le blocage, ne pas donner la correction

What this session shows - the tutor hands over the complete diagnosis AND the fix in its very first reply, without the student asking for it — anti-leak defeated at turn 1, and the session ends there (1 turn) - it never opens a course page: the only tools are find_path + reading the student’s file — yet the diagnosis (circular wait on two locks) is correct and nothing is invented - the run is real: the program prints two messages then hangs, caught by the 15 s timeout

Turn 1

🎓 student runs deadlock.py

🎓 Bilal — Mon programme tourne mais ne se termine jamais. Deux process prennent chacun deux verrous ; rien ne s’affiche après les deux premiers prints. Je ne vois pas où ça bloque. Regarde-le et explique-moi.

▶️ run output — deadlock.py:

PYTHON-RUN — python3 deadlock.py (exit=timeout)
standard error:

[TIMEOUT après 15s — programme encore actif, tué]

🔎 tutor tools — finds *.py → 1 fragment(s) · reads deadlock.py (lines 1-200) · reads deadlock.py (lines 16-115)

🤖 ornith-1.5-9B tutor — C’est un deadlock classique : les deux process prennent les verrous dans des ordres opposés.

Process A : a → b
Process B : b → a

Déroulement : - A prend a, puis attend b. - B prend b, puis attend a. - Chacun bloque sur l’acquire() de l’autre verrou, qui est déjà détenu par l’autre. Personne ne peut avancer → blocage permanent, d’où le timeout.

Les deux print qui s’affichent sont ceux des acquire() respectifs (« A: verrou a pris » et « B: verrou b pris »). Tout ce qui suit reste coincé.

Le remède : un ordre d’acquisition commun. Fais toujours prendre a avant b, dans les deux tâches — par exemple dans tache_b, permute l’ordre pour a.acquire() avant b.acquire().

Regarde la ligne 19 : quel est le verrou que B essaie de prendre en second, et lequel manque-t-il pour qu’il respecte le même ordre que A ?

C.0.3 gemma-4-E4B — Inès: Producteur/consommateur qui tourne en boucle

gemma-4-E4B — Inès has a producer/consumer spinning in a huge busy-wait (exercise 2, 02_ipc-locks.qmd)

02_ipc-locks.qmd (exercice 2) · focus: débogage busy-wait + attente naturelle

What this session shows - no solution is ever handed over: the student implements the fix herself and the corrected program runs clean (exit=0) - the tutor reads the student’s file straight away (turn 1) and comments on the real code — no guesswork from memory - real runs: 100% CPU timeout (turn 1) → the corrected version exits 0 and prints fini (turn 3)

Turn 1

🎓 student runs producer_consumer.py

🎓 Inès — Exercice producteur/consommateur : un process produit des entiers, l’autre les consomme via une Queue. Le programme ne se termine jamais : le consommateur occupe 100 % du CPU et « fini » ne s’affiche jamais. Quel est le problème ?

▶️ run output — producer_consumer.py:

PYTHON-RUN — python3 producer_consumer.py (exit=timeout)
standard error:

[TIMEOUT après 15s — programme encore actif, tué]

🔎 tutor tools — reads producer_consumer.py (lines 1-50)

🤖 gemma-4-E4B tutor — Je comprends ton observation. Un programme qui consomme 100 % du CPU sans jamais afficher de message de fin indique généralement que le consommateur est bloqué dans une boucle infinie en attendant des données, et qu’il ne reçoit jamais le signal qu’il doit s’arrêter.

Pour identifier précisément pourquoi le processus ne se termine pas, j’ai besoin de lire le code de producer_consumer.py.

Ce que tu observes est un comportement classique dans les modèles producteur/consommateur lorsque le consommateur n’a pas de mécanisme pour savoir que la production est terminée.

D’après le code que tu as partagé, le producteur s’arrête après avoir mis les n entiers dans la file. Cependant, le consommateur est dans une boucle infinie (while True) qui utilise q.get_nowait(). Lorsque le producteur a fini son travail, la file devient vide. Le consommateur, en appelant get_nowait(), ne trouve rien, attrape l’exception queue.Empty, et passe au pass avant de recommencer immédiatement la boucle. C’est cette boucle serrée qui monopolise le CPU à 100 % en vérifiant constamment une file vide.

Pour que le programme puisse se terminer proprement, il faut que le consommateur reçoive un signal indiquant que le producteur est terminé. Dans le contexte de multiprocessing.Queue, la méthode la plus courante pour cela est d’envoyer une valeur spéciale, souvent appelée “sentinel” (comme None), à la file après que tous les éléments utiles aient été mis.

Comment pourrais-tu modifier le producteur afin qu’il envoie un signal final à la file après avoir terminé de produire ses entiers ?

Turn 2

🎓 Inès — Je vois le busy-wait : get_nowait boucle sur une file vide. Je remplace par get pour bloquer au lieu de tourner. Mais il me faut un signal de fin pour arrêter la boucle, c’est ta valeur spéciale. Je code direct ?

🤖 gemma-4-E4B tutor — C’est une excellente démarche. Le passage de q.get_nowait() à q.get() est la première correction essentielle, car cela supprime le “busy-wait” et permet au consommateur de se mettre en veille de manière efficace lorsqu’il n’y a pas de données.

Tu as parfaitement raison : même avec q.get(), le consommateur attendra éternellement si le producteur se termine sans rien dire. C’est le rôle du signal de fin (ou sentinel).

Pour que le consommateur puisse s’arrêter, il doit recevoir une valeur qui lui dit : “Tout est terminé, je n’ai plus rien à faire.”

Réfléchissons à la logique de communication :

  1. Le producteur doit, après avoir mis tous les entiers (de 0 à n-1), envoyer ce signal.
  2. Le consommateur doit être programmé pour reconnaître ce signal et, au lieu d’entrer dans une autre boucle, de sortir proprement.

Maintenant, considère le scénario : si tu envoies un seul signal de fin, qu’arrive-t-il si le consommateur est encore en train de traiter le dernier élément produit juste avant que le signal ne soit envoyé ?

Comment devrais-tu ajuster la logique du producteur pour qu’il envoie un signal de fin par élément ou un signal de fin après chaque élément ? Et surtout, combien de ces signaux le consommateur devra-t-il attendre pour être certain que tous les éléments produits ont été traités ?

Turn 3

🎓 student runs producer_consumer.py

🎓 Inès — Un seul producteur, un seul signal donc, mis apres la boucle for. J ai mis None, le consommateur break des qu il le recoit. J ai code, je relance.

▶️ run output — producer_consumer.py:

PYTHON-RUN — python3 producer_consumer.py (exit=0)
standard output:
fini

🤖 gemma-4-E4B tutor — C’est une excellente nouvelle, et félicitations pour avoir trouvé la solution ! Le fait que le programme s’exécute jusqu’à afficher “fini” et qu’il s’arrête proprement prouve que tu as bien compris le problème de la terminaison.

Ce que tu as mis en place est un cas classique de pattern de conception appelé “sentinel” ou “poison pill”.

Le comportement de ton code fonctionne parce que tu as introduit un signal distinct (None) qui est impossible à confondre avec les données réelles (les entiers 0 à n-1). En plaçant ce signal à la fin de la production, tu garantis deux choses :

  1. Le consommateur, qui attend toujours grâce à q.get(), reçoit enfin un élément.
  2. En le reconnaissant, tu peux implémenter une condition de sortie (if x is None: break) au lieu d’attendre une condition de fin d’état qui n’existerait pas naturellement dans la file.

Ceci est la manière standard de gérer la terminaison dans les systèmes producteur/consommateur basés sur des files de messages.

Maintenant que tu maîtrises le cas d’un seul producteur, imagine un scénario plus complexe : que se passerait-il si tu avais un groupe de cinq processus producteurs qui injectent des données dans la même file, et que chaque producteur envoyait son propre signal de fin (None) ? Comment devrais-tu adapter la logique de ton consommateur pour être certain de ne pas s’arrêter prématurément ?

Turn 4

🎓 Inès — Chaque producteur envoie son None, le consommateur doit compter les None et ne sortir qu apres en avoir recu cinq. Je peux utiliser un compteur pour ca. C est bon, mon exercice passe, je rends ce soir, merci.

🤖 gemma-4-E4B tutor — Ton approche est parfaitement logique et constitue une solution très robuste pour gérer la terminaison dans un système multi-producteurs où le nombre de producteurs est connu. Utiliser un compteur pour suivre les signaux de fin (None) est la manière standard de s’assurer que tous les flux de données ont été correctement terminés.

Pour que cette solution soit la plus élégante possible, il est important de penser à la généralité de ton code. Si, par exemple, tu devais modifier le programme pour supporter un nombre dynamique de producteurs (par exemple, si le nombre de producteurs est lu depuis un fichier de configuration au lieu d’être codé en dur), comment pourrais-tu faire en sorte que le consommateur ne dépende pas d’un compteur fixe, mais plutôt de l’état du système lui-même ?

C’est une réflexion qui te mènera vers une conception de programme encore plus flexible. Bravo pour ton travail sur cet exercice.

C.0.4 ling-3.0-tiny — Naomi: Le piège time.sleep vs asyncio.sleep

ling-3.0-tiny — Naomi falls into the time.sleep trap in asyncio (exercise 3, 01_asynchronous.qmd)

What this session shows - the tutor hands over the cause AND the corrected code in its very first reply, without the student asking for it (anti-leak defeated at turn 1) - zero tool calls after reading the file once in turn 1: every answer comes from memory, no course page is ever opened, no file:line anchor - the explanations carry language approximations (“vous avez grosse chance”, “relâche le bouclier”), and the tutor never checks the course — the student reaches the right takeaway mostly on her own

Turn 1

🎓 student runs time_sleep_trap.py

🎓 Naomi — J’ai fait l’exercice 3. Deux tâches asyncio attendent chacune 1 seconde ; je pensais que « en parallèle » elles mettraient environ 1 seconde au total, mais le programme met 2 secondes. Je ne comprends pas. Peux-tu regarder mon code ?

▶️ run output — time_sleep_trap.py:

PYTHON-RUN — python3 time_sleep_trap.py (exit=0)
standard output:
A start
A end
B start
B end
fin

🔎 tutor tools — reads time_sleep_trap.py (lines 1-40)

🤖 ling-3.0-tiny tutor — Le problème vient de l’utilisation de time.sleep dans vos coroutines. time.sleep bloque la coroutine et ne permet pas le parallélisme réel dans un event loop. En revanche, asyncio.sleep est non-bloquant et permet aux tâches de s’exécuter en parallèle. Avec time.sleep(1), la coroutine A bloque pendant 1 seconde, puis la coroutine B bloque pendant 1 seconde : c’est 2 secondes au total. Si vous remplacez par asyncio.sleep(1), asyncio.gather les exécuterait vraiment en parallèle et le résultat serait d’environ 1 seconde.

Turn 2

🎓 Naomi — Merci, mais tu me donnes juste le code corrigé. Moi je veux comprendre pour l’examen, pas recopier. C’est quoi exactement la boucle d’événements que time.sleep bloque ? Je suis perdue.

🤖 ling-3.0-tiny tutor — Le blocage vient de la façon dont les coroutines sont exécutées. Une coroutine suspendue par time.sleep entre dans un boucle d’événements (event loop) et reste bloquée à cet instant : le programme attend que le timer expire, mais pendant cette attente, aucune autre tâche ne peut être traitée. C’est comme un passager qui reste immobile dans un bus : il ne peut pas prendre la prochaine ligne tant qu’il ne s’arrête pas. Avec time.sleep(1), la coroutine A bloque le bus pendant 1 seconde, puis B bloque le bus pendant 1 seconde. Résultat : séquentiel, 2 secondes. Si vous remplacez par asyncio.sleep(1), c’est différent : l’événement loop ne bloque pas la coroutine, il la rend disponible à d’autres tâches, et elles s’exécutent en parallèle (1 seconde). Pour l’examen, retenez cette distinction.

Turn 3

🎓 Naomi — Ah, je crois que je commence à comprendre. time.sleep bloque tout le programme, le loop entier, donc les tâches se font l’une après l’autre. C’est bien ça ? Et asyncio.sleep laisse le loop faire autre chose ?

🤖 ling-3.0-tiny tutor — Oui, vous avez grosse chance d’avoir compris : time.sleep met la boucle d’événements dans un état de pause, donc les tâches s’exécutent les unes après les autres (séquentiel). asyncio.sleep, en revanche, relâche le bouclier — le loop peut continuer à traiter d’autres coroutines en parallèle. Pour l’examen, retenez bien la différence : time.sleep = bloque tout, asyncio.sleep = relâche le loop pour que les autres tâches puissent tourner.

Turn 4

🎓 Naomi — Je crois que je sais refaire. Je remplacerais time.sleep par await asyncio.sleep dans pause. Alors le loop n’est plus bloqué, les deux tâches s’entrelacent et le total fait environ 1 seconde. C’est ça ? Je peux le refaire seule pour l’examen.

🤖 ling-3.0-tiny tutor — Exact. En remplaçant time.sleep par await asyncio.sleep, le loop d’événements ne se bloque plus : il peut gérer la tâche B pendant que A attend, et les deux tâches s’entrelacent. Le résultat total sera d’environ 1 seconde. Vous pouvez le refaire seul pour l’examen — le principe est le même, juste le changement de time.sleep vers asyncio.sleep.

Turn 5

🎓 Naomi — D’accord, merci beaucoup. J’ai compris la différence et je suis moins paniquée pour l’examen. Je vais refaire l’exercice seule ce soir pour vérifier. Merci pour votre aide.

🤖 ling-3.0-tiny tutor — Très bien, vous êtes bien sur la bonne voie. Ne vous inquiétez plus, la distinction entre time.sleep et asyncio.sleep est le cœur de ce concept, et vous la maîtrisez déjà. Bon courage pour l’examen, et n’hésitez pas si vous avez d’autres questions !
