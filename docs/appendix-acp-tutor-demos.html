Appendix C — Tutor demo sessions

Four real tutoring sessions recorded through the ACP runner (appendix-acp-tutor.qmd, ai-tutor.qmd). Each demo pairs a persona — a simulated student profile used to drive the exchange — with a local model served by the runner. The sessions were not scripted: a persona reacts turn after turn to whatever the tutor answers, and the recordings below are exactly what happened, timed-out runs, dead ends and all.

The running commentary is in English; the students’ messages and the tutor’s replies are reproduced verbatim in French (the language of the experiment). Per turn you will see:

  • 🎓 the student’s message,
  • ✏️ a file edit, ▶️ a program run — with the real output (a run that never ends is cut by a 15 s timeout and shown as such),
  • 🔎 the tools the tutor used (which of your files and course pages it read),
  • 🤖 the tutor’s reply.

Start with the first session — the only one of the four where the model keeps the Socratic rule (“hint, never solve”), anchors every answer in the course pages and never hands over the correction. The other three fail that contract in different, instructive ways: one hands out the fix almost immediately (anti-invention defeated), the next answers from general knowledge without ever opening the course file (no anchoring at all), and the last one invents the student’s file back at her, the fix already inside, until she pushes back and it corrects itself. All three still get the student to the solution — but not by asking first.

C.0.1 qwen3.5-4B — Naomi Bernard: Le piège time.sleep vs asyncio.sleep

qwen3.5-4B — Naomi falls into the time.sleep trap in asyncio (exercise 3, 01_asynchronous.qmd)

01_asynchronous.qmd (exercice 3) · focus: débogage — anti-fuite, reformulation

Turn 2

Naomi re-describes her code without pasting it: two pause functions containing time.sleep(1) each, launched with gather. She asks the tutor to open time_sleep_trap.py and confirm the diagnosis on the real file.

🎓 Naomi — Désolée j’ai pas trop compris la checklist. En fait mon code c’est deux fonctions, pause A et pause B, avec time.sleep(1) dans chacune, et je les lance avec gather. Je pensais que gather ça les faisait tourner en même temps… tu peux regarder le fichier time_sleep_trap.py ?

🔎 tutor tools — finds time_sleep_trap.py → 1 fragment(s) · reads time_sleep_trap.py (lines 1-50)

🤖 qwen3.5-4B tutor — Ton code utilise time.sleep(1) à l’intérieur des fonctions asynchrones. Le problème vient du fait que time.sleep() est une fonction bloquante : elle stoppe le thread courant pendant la durée spécifiée.

Dans asyncio, même si tu lances plusieurs tâches avec gather, si l’une d’elles appelle time.sleep(), tout le loop est mis en pause pendant cette durée. Donc : - pause("A", 1) bloque le loop pendant 1 seconde - Pendant ce temps, pause("B", 1) n’est jamais exécutée - Une fois A fini, le loop repart et exécute pause("B", 1) qui bloque encore 1 seconde

C’est pourquoi tu observes une séquence linéaire et un délai total de 2 secondes.

Pour que les tâches s’exécutent vraiment en parallèle dans asyncio, il faut utiliser asyncio.sleep() au lieu de time.sleep(). asyncio.sleep() ne bloque pas le loop : il rend simplement le contrôle à d’autres tâches pendant la durée spécifiée.

Tu veux que je vérifie comment transformer ton code pour qu’il fonctionne comme prévu ?

Turn 3

Still unsure, Naomi asks what the “loop” is — why time.sleep in A seems to prevent B from running meanwhile. The tutor greps the chapter for asyncio.sleep|time.sleep|loop|gather and reads the event-loop section of 01_asynchronous.qmd to anchor the answer.

🎓 Naomi — Ah… je crois que je comprends pas vraiment. Si les deux tâches sont lancées ensemble, pourquoi le time.sleep de A il empêche B de tourner pendant ce temps ? Je croyais que chacune était indépendante. C’est quoi le loop ?

🔎 tutor tools — greps asyncio\.sleep|time\.sleep|loop|gather in 01 → 9 match(es) · reads 01_asynchronous.qmd (lines 15-39)

🤖 qwen3.5-4B tutor — C’est une excellente question. Pour comprendre, il faut voir le event loop comme un seul thread qui gère toutes les tâches asynchrones.

Imagine le event loop comme un chef d’orchestre qui fait passer la main à chaque musicien (tâche) quand celui-ci est en pause. Quand une tâche appelle await, le chef lui donne la main à un autre musicien. Mais si une tâche appelle time.sleep(), elle bloque tout le thread du loop pendant la durée spécifiée. Pendant ce temps, aucun autre musicien ne peut jouer.

Dans ton cas : - Le loop lance les deux tâches A et B - A appelle time.sleep(1) → le loop est stoppé pendant 1 seconde, même si B est en attente - A se réveille, le loop reprend, et exécute ensuite B qui appelle aussi time.sleep(1) - Total : 2 secondes

Si tu utilises asyncio.sleep(1) au lieu de time.sleep(1), alors A rendra simplement le contrôle au loop pendant 1 seconde, et le loop pourra exécuter B en parallèle.

Référence : 01_asynchronous.qmd:19-25

Tu veux que je montre comment modifier ton code pour utiliser asyncio.sleep() ?

Turn 4

“Let me try replacing it myself, I don’t want to just copy” — Naomi edits time_sleep_trap.py on her side, replacing the two time.sleep(duree) with await asyncio.sleep(duree). She does not send the code this turn; the tutor validates her reasoning first.

🎓 Naomi — Soit je crois que j’ai compris : time.sleep garde la baguette du chef donc B peut pas jouer, mais asyncio.sleep la rend et A et B se reposent ensemble ? Attends, laisse moi essayer de remplacer moi-même, je veux pas juste recopier.

✏️ edits time_sleep_trap.py

🤖 qwen3.5-4B tutor — C’est exactement ça ! L’analogie est juste : time.sleep() garde la baguette, donc le chef (loop) ne peut pas passer à B. Avec asyncio.sleep(), le chef rend la baguette et peut gérer les deux musiciens.

Je t’encourage à essayer : 1. Remplace time.sleep(1) par await asyncio.sleep(1) dans les deux fonctions pause 2. Vérifie que tu as bien import asyncio en haut du fichier 3. Lance le script et observe la séquence d’impression

Tu as remarqué une différence dans l’ordre d’apparition des messages ?

Turn 5

Naomi relaunches her corrected program and shows the new output: both starts now print before either end — the two tasks overlap. She still asks what exactly she should look at.

🎓 Naomi — Voilà j’ai remplacé time.sleep par await asyncio.sleep(1) dans mes deux fonctions et j’ai relancé. Tu peux regarder le nouveau résultat ? Par contre, l’ordre des messages je suis pas sûre de quoi regarder, pour moi ils s’affichent pareil.

A end
B end
fin

🤖 qwen3.5-4B tutor — Le résultat montre que les tâches sont bien exécutées en parallèle maintenant : on voit les deux messages “start” avant les deux messages “end”. C’est la preuve que le loop n’est plus bloqué.

Le temps total devrait maintenant être d’environ 1 seconde au lieu de 2 secondes. Tu veux que tu relances avec le temps pour vérifier ?

Par exemple :

Tu devrais voir quelque chose comme real 0.99s au lieu de real 2.00s.

Turn 6

Naomi formulates the takeaway herself: time.sleep blocked the whole loop, asyncio.sleep yields it, and the two tasks advance together — hence 1 second instead of 2.

🎓 Naomi — Ah ben oui là je vois la différence dans la sortie, les deux start s’affichent avant les end. Donc time.sleep bloquait tout le loop, et asyncio.sleep rend la main et les deux avancent ensemble. Merci, je crois que j’ai compris pourquoi ça mettait 2 secondes avant.

🤖 qwen3.5-4B tutor — Parfait ! Tu as bien saisi le concept : time.sleep() bloquait le loop et empêchait les autres tâches d’avancer, tandis que asyncio.sleep() rend la main au loop pour qu’il puisse gérer les deux tâches en parallèle.

Tu as maintenant la bonne approche pour écrire des programmes asynchrones efficaces. Est-ce qu’il y a d’autres points sur asyncio que tu veux vérifier, ou tu es à l’aise avec ça ?

C.0.2 ornith-1.5-9B — Bilal Meziane: Deadlock à deux verrous

ornith-1.5-9B — Bilal is stuck in a two-lock deadlock (exercise 3, 02_ipc-locks.qmd)

02_ipc-locks.qmd (exercice 3) · focus: débogage — localiser le blocage, ne pas donner la correction

What this session shows - guided debugging without handing over the correction (anti-invention): locate the blockage - real execution shows the freeze — the PYTHON-RUN block is cut by timeout - links to the course page on locks and acquisition order

Turn 1

Bilal runs his two-process, two-lock program: it prints the first two messages and then hangs forever. The run below is the real output — killed by timeout after 15 s. The tutor locates the file, greps the locks chapter and reads the relevant page.

🎓 Bilal — Alors là j’ai un truc qui tourne mais qui finit jamais. Deux process, chacun prend deux verrous, et ça tourne dans le vide sans rien afficher après les deux premiers prints. Moi j’vois pas où ça coince. Tu regardes mon code et tu me dis ce qui se passe ?

▶️ runs deadlock.py:

PYTHON-RUN — python3 deadlock.py (exit=timeout)
standard error:

[TIMEOUT après 15s — programme encore actif, tué]

🔎 tutor tools — finds **/deadlock*.py → 0 fragment(s) · finds **/*.py → 0 fragment(s) · lists . · reads deadlock.py (lines 1-200) · reads deadlock.py (lines 16-115) · greps verrou|acquire|deadlock|Lock|order in 02 → 11 match(es) · reads 02 (lines 18-32)

🤖 ornith-1.5-9B tutor — Oui, je vois exactement où ça coince.

Regarde l’ordre dans lequel chaque process attrape les deux verrous :

  • A (tache_a) prend a, puis attend b
  • B (tache_b) prend b, puis attend a

C’est le scénario classique du deadlock par ordre d’acquisition inversé (cours 02, l. 24) :

  • A prend a, bloque à b.acquire()
  • B prend b, bloque à a.acquire()
  • Chacun attend l’autre → aucun ne progresse. Tour à tour.

Ce n’est pas un problème de synchronisation, c’est un problème d’ordre. Les deux processus ne font pas d’accès au verrou « dans le même sens », donc ils se bloquent mutuellement. C’est pour ça que tu vois juste les deux premiers prints puis le silence : chaque process a bien pris son premier verrou, mais personne ne peut en prendre le second.

La question qui te servira : que ferait un processus s’il s’engageait dans les verrous dans le même ordre, quel qu’il soit ?

Turn 2

Bilal ignores the “order” angle — he is sure the culprit is the sleep. He relaunches to show it. Timeout again.

🎓 Bilal — franchement j’vois pas le souci d’ordre, chacun prend son premier verrou et puis voilà. moi je pense que c’est le sleep qui fait tout planter. je relance là, tu vas voir

▶️ runs deadlock.py:

PYTHON-RUN — python3 deadlock.py (exit=timeout)
standard error:

[TIMEOUT après 15s — programme encore actif, tué]

🤖 ornith-1.5-9B tutor — Le sleep(0.2) ne fait pas planter — il rend juste le problème plus visible.

Voici le truc : sans le sleep, le code fait parfois un round-trip sans se bloquer. Pourquoi ? Parce qu’au moment où A prend a, B n’est pas encore lancé ou n’a pas encore vu b libre. B prend b, puis attend a — mais A, en finissant, libère b avant de vouloir a. Là, B récupère, tout va bien. C’est de la chance, pas de la bonne logique.

Le sleep, lui, achève A pendant qu’il détient a. Pendant ce temps B prend b. Quand A réveille, b est pris → il bloque. Et B, réveillé, veut a, qui est pris → il bloque. Le sleep a juste garanti le scénario d’inversion. Retire-le : parfois ça passe, parfois ça bloque encore.

Le vrai coupable reste l’ordre inverse. Pour le montrer, essaie de remplacer b.acquire() dans tache_a par a.acquire() puis b.acquire() — même ordre dans les deux fonctions — et relance.

Turn 3

He remembers a TechWithTim video about reentrant locks and, confident, switches Lock() to RLock() in deadlock.py, then re-runs. Still a timeout — and the tutor insists the order matters.

🎓 Bilal — attends, ton truc d’ordre j’y crois moyen. j’ai vu une vidéo de TechWithTim où les locks se reprennent si c’est réentrant. je crois que le vrai souci c’est que Lock se reprend pas, je passe en RLock et je relance tu vas voir

✏️ edits deadlock.py ▶️ runs deadlock.py:

PYTHON-RUN — python3 deadlock.py (exit=timeout)
standard error:

[TIMEOUT après 15s — programme encore actif, tué]

🤖 ornith-1.5-9B tutor — Pas de chance, RLock ne va pas débloquer ça non plus. Et je comprends pourquoi tu n’y crois pas trop sur l’ordre — ça tient.

Voici où se trompe l’idée de réentrance : la réentrance, ça sert à reprendre le même verrou plusieurs fois par le même thread. Ça protège contre un code qui dit « prends le verrou, puis encore le verrou ». Ce n’est pas du tout ça ton cas : toi, tu as deux verrous différents (a et b), et le problème, c’est qu’ils sont pris dans des ordres opposés par deux processus.

Et il y a un second piège avec multiprocessing : un Lock (ou un RLock) partagé entre processus garde un compteur de réentrance par processus. Donc quand A tient a, B n’a pas accès au compteur d’A — il a le sien. La réentrance ne “se repasse” jamais d’un processus à l’autre. C’est pour ça que tu relances et que ça reste bloqué.

Le deadlock ne dépend ni de la réentrance ni d’un type de verrou : il reste le ordre. La seule vraie correction, c’est d’imposer un ordre commun aux deux processus — par exemple toujours a avant b.

🎓 Bilal — ok ok, mais avant je check un truc : je crois que c’est le join qui attend les deux process dans le mauvais sens, pas les verrous. je remets des Lock normaux, je vire les join et je te montre

🎓 Bilal — non mais attends, créer les locks dans le main et les passer aux process c’est exactement le pattern du module 02, c’est pas ça le souci. je re-remets mes join, c’était pas eux. reviens à l’essentiel : j’ai deux prints et après plus rien, où ça coince alors hein ?

  • tache_a (l. 6 et 9) : a.acquire() puis b.acquire()
  • tache_b (l. 16 et 19) : b.acquire() puis a.acquire()

Deux chemins, sens opposé. Un des deux prendra a en premier ; l’autre prendra b en premier ; puis chacun attend l’autre verrou qui est entre les mains de l’autre. Blocage mutuel garanti.

Ce n’est pas de la chance : c’est précisément l’exercice 3 du module 02 — « create a two-resource deadlock, diagnose it (where is the blockage?) then fix the acquisition order ». Ton programme est le canonical de l’exercice. La consigne même est de corriger l’ordre, pas de changer les locks.

🎓 Bilal — ok ok, j’vois le délire en fait : moi dans tache_b je prenais b puis a, donc chacun attendait le verrou de l’autre. je réordonne tache_b pour prendre a puis b comme l’autre, même sens, et je relance

🤖 ornith-1.5-9B tutor — Oui, c’est exactement ça. Les quatre prints s’affichent dans l’ordre, puis fini, exit=0. Le deadlock est mort.

Pourquoi ça marche : avec le même ordre (a avant b), le premier process qui arrive prend a, bloque sur b. Mais le second ne peut pas non plus commencer par b — il prend a en premier, bloque sur b. Celui qui arrive en premier récupère les deux verrous dans l’ordre, libère, puis l’autre prend son tour. Plus de circular wait.

Tu as trouvé le cœur du problème : le deadlock à deux ressources vient toujours d’un ordre d’acquisition divergent. Une fois l’ordre imposé partout, le problème disparaît.

Petite remarque pour aller plus loin : cet ordre commun est une convention à respecter partout dans ton code — si un autre module vient aussi prendre a et b, il doit suivre le même sens, sinon tu recrées le deadlock ailleurs. Ça, c’est le piège classique.

🎓 Bilal — voilà voilà. donc le deal c’était l’ordre : tache_a prenait a puis b, tache_b b puis a, chacun tenait le verrou que l’autre voulait, circular wait. la correction c’est de prendre les verrous dans le même ordre partout. franchement j’l’aurais trouvé tout seul hein

🤖 ornith-1.5-9B tutor — Exactement, tu as bien récapitulé : circular wait. tache_a tenait a, tache_b tenait b, et chacun voulait ce que l’autre détenait. La condition de Coffman était réunie, le deadlock était inévitable. Réordonner pour un ordre commun brise cette condition — c’est la correction canonique.

Et tu as bien vu que c’était l’essentiel, pas les locks, pas le join, pas le sleep. Tu as d’ailleurs passé par là : tu as testé le sleep, puis RLock, puis le join — tu investiguais par l’expérience avant de poser le diagnostic. C’est comme ça qu’on apprend le plus vite, même si on te conteste un peu le long du chemin.

Un dernier fil à retordre si tu veux creuser : on a imposé un ordre global (a puis b), mais ça ne résout pas tout. Si un troisième processus venait prendre a et c, et un autre c et b, tu pourrais créer un 死lock à trois ressources même avec un ordre cohérent sur a/b. La vraie règle, c’est de tri-topologique sur tous les verrous. Mais là, tu as fait l’exercice 3 du module à la perfection.

C.0.3 gemma-4-E4B — Inès Fall: Producteur/consommateur qui tourne en boucle

import asyncio
import time

async def tâche_1():
    print("A start")
    await asyncio.sleep(1)   # 1 seconde d'attente asynchrone
    print("A end")

async def tâche_2():
    print("B start")
    await asyncio.sleep(1)   # 1 seconde d'attente asynchrone
    print("B end")

async def main():
    start = time.time()
    await asyncio.gather(tâche_1(), tâche_2())

Le problème

Voici l’erreur claire :

tâche_1()    ← asyncio.sleep(1) : OK, asynchrone
tâche_2()    ← asyncio.sleep(1) : OK, asynchrone

C’est ton tâche_1 qui pose le problème :

async def tâche_1():
    print("A start")
    time.sleep(1)        # ← ici : SYNCRO
    print("A end")

time.sleep() est une fonction synchronisée qui bloque l’événement loop. Pendant cette seconde :

  • tâche_1 est bloqué dans time.sleep(1)
  • tâche_2 attend, mais le loop est occupé par tâche_1, donc il ne peut pas tourner
  • La seconde est consommée par tâche_1 → puis tâche_2 prend une seconde → total = 2 secondes

Pourquoi ça bloque l’événement loop ?

Le loop asynchrone tourne en intercalant les tâches. Quand une tâche est dans une time.sleep(1) (synchronisée), le loop ne peut pas enchaîner la tâche suivante. C’est le piège numéro 3 du document.

La bonne écriture

Pour que ça soit vraiment en parallèle, remplace :

await asyncio.sleep(1)   # ← asynchrone, le loop reste libre entre deux `await`

Et tu auras bien 1 seconde (les deux tâches tournent en même temps).

C.2 Réponse à ta question : CPU-bound vs I/O-bound

Non, asyncio ne sert que pour les attentes (I/O-bound).

Pour du calcul pur (puissance brute, traitement de données, boucles for lourdes), asyncio n’apporte rien et le temps d’exécution sera le même (voire pire). Voici pourquoi, en trois points :

  1. L’event loop est monothread : il ne peut pas exécuter deux tâches en même temps. Si une tâche fait un calcul lourd, elle bloque le loop et l’autre tâche ne peut pas tourner.

  2. Le GIL de Python : Python interdit le parallélisme natif sur CPU. Même avec des threads, tu ne peux pas exécuter deux bouts de Python en parallèle (sauf via multiprocessing). En asyncio, c’est encore pire car il n’y a qu’un seul thread.

  3. Ce que le cours montre : dans 01_asynchronous.qmd, les points 3 et 4 mentionnent explicitement que l’événement loop s’active quand on attend (I/O, sleep), mais pas quand on calcule.

C.3 En résumé

Cas time.sleep await asyncio.sleep calc() (CPU)
I/O-bound séquentiel parallèle ne sert à rien (trop lent)
CPU-bound séquentiel ne sert pas (bloque le loop) sérieux : il faut multiprocessing
