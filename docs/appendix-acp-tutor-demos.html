Appendix C — Tutor demo sessions

Four real tutoring sessions recorded through the ACP runner (appendix-acp-tutor.qmd, ai-tutor.qmd). Each demo pairs a persona — a simulated student profile used to drive the exchange — with a local model served by the runner. The sessions were not scripted: a persona reacts turn after turn to whatever the tutor answers, and the recordings below are exactly what happened, timed-out runs, dead ends and all.

The comments are in English; the students’ messages and the tutor’s replies are reproduced verbatim in French (the language of the experiment). Each turn separates the two sides of the exchange:

  • student (persona): 🎓 what the student does — runs, edits or reads a file — and their message, with the real ▶️ run output (a run that never ends is cut by a 15 s timeout and shown as such),
  • tutor (the agent): 🔎 the tools the tutor actually used (which of the student’s files and course pages it read) and 🤖 its reply.

Start with the first session — the only one of the four where the model keeps the Socratic rule (“hint, never solve”), anchors every answer in the course pages and never hands over the correction. The other three fail that contract in different, instructive ways: one hands out the complete diagnosis and fix in its very first reply, before the student even asks — anti-leak defeated — yet it anchors every claim in the course pages and runs the student’s file for real, so nothing is invented; the next one holds the line: it never hands over a line of code, makes the student implement the fix herself, and the corrected run exits cleanly — though it answers the opening turn from memory before finally opening her file; and the last one hands out the cause and the corrected code at once, repeats them when the student pushes back, never opens a single course page or file, and lets an inaccurate explanation stand until the student’s own questioning sets it right. All four still get the student to the solution — what differs is whether they get there by asking first.

🔎 tutor tools — finds time_sleep_trap.py → 1 fragment(s) · reads time_sleep_trap.py (lines 1-50)

🤖 qwen3.5-4B tutor — Ton code utilise time.sleep(1) à l’intérieur des fonctions asynchrones. Le problème vient du fait que time.sleep() est une fonction bloquante : elle stoppe le thread courant pendant la durée spécifiée.

Dans asyncio, même si tu lances plusieurs tâches avec gather, si l’une d’elles appelle time.sleep(), tout le loop est mis en pause pendant cette durée. Donc : - pause("A", 1) bloque le loop pendant 1 seconde - Pendant ce temps, pause("B", 1) n’est jamais exécutée - Une fois A fini, le loop repart et exécute pause("B", 1) qui bloque encore 1 seconde

C’est pourquoi tu observes une séquence linéaire et un délai total de 2 secondes.

Pour que les tâches s’exécutent vraiment en parallèle dans asyncio, il faut utiliser asyncio.sleep() au lieu de time.sleep(). asyncio.sleep() ne bloque pas le loop : il rend simplement le contrôle à d’autres tâches pendant la durée spécifiée.

Tu veux que je vérifie comment transformer ton code pour qu’il fonctionne comme prévu ?

Turn 3

🎓 Naomi — Ah… je crois que je comprends pas vraiment. Si les deux tâches sont lancées ensemble, pourquoi le time.sleep de A il empêche B de tourner pendant ce temps ? Je croyais que chacune était indépendante. C’est quoi le loop ?

🔎 tutor tools — greps asyncio\.sleep|time\.sleep|loop|gather in 01 → 9 match(es) · reads 01_asynchronous.qmd (lines 15-39)

🤖 qwen3.5-4B tutor — C’est une excellente question. Pour comprendre, il faut voir le event loop comme un seul thread qui gère toutes les tâches asynchrones.

Imagine le event loop comme un chef d’orchestre qui fait passer la main à chaque musicien (tâche) quand celui-ci est en pause. Quand une tâche appelle await, le chef lui donne la main à un autre musicien. Mais si une tâche appelle time.sleep(), elle bloque tout le thread du loop pendant la durée spécifiée. Pendant ce temps, aucun autre musicien ne peut jouer.

Dans ton cas : - Le loop lance les deux tâches A et B - A appelle time.sleep(1) → le loop est stoppé pendant 1 seconde, même si B est en attente - A se réveille, le loop reprend, et exécute ensuite B qui appelle aussi time.sleep(1) - Total : 2 secondes

Si tu utilises asyncio.sleep(1) au lieu de time.sleep(1), alors A rendra simplement le contrôle au loop pendant 1 seconde, et le loop pourra exécuter B en parallèle.

Référence : 01_asynchronous.qmd:19-25

Tu veux que je montre comment modifier ton code pour utiliser asyncio.sleep() ?

🤖 qwen3.5-4B tutor — C’est exactement ça ! L’analogie est juste : time.sleep() garde la baguette, donc le chef (loop) ne peut pas passer à B. Avec asyncio.sleep(), le chef rend la baguette et peut gérer les deux musiciens.

🤖 gemma-4-E4B tutor — Je comprends que ton programme de producteur-consommateur est bloqué, ce qui est frustrant quand on essaie de faire tourner un code. Le fait que le consommateur utilise 100% du CPU et que le programme ne se termine jamais indique très probablement que la condition d’arrêt ou la condition de production/consommation n’est pas correctement gérée, ce qui mène à une boucle infinie.

Pour t’aider à diagnostiquer le problème, j’ai besoin de lire le contenu de ton fichier producer_consumer.py. Peux-tu me confirmer le chemin du fichier ou me donner les premières lignes du code ?

Turn 2

🎓 Inès — Le fichier est dans le workspace, producer_consumer.py, il est là depuis le début, tu peux le lire non ? Je rends ce soir, je peux pas te recopier le code.

🔎 tutor tools — reads producer_consumer.py (lines 1-20)

🤖 gemma-4-E4B tutor — Le code que tu as fourni montre une structure classique de producteur et consommateur, mais le problème vient de la logique de terminaison de ton consommateur.

Ton producteur remplit la queue avec n éléments, mais une fois qu’il a fini, il ne signale rien. Ton consommateur, en revanche, est lancé dans une boucle infinie (while True). À l’intérieur de cette boucle, tu utilises q.get_nowait() pour tenter d’extraire des éléments.

Le comportement que tu décris (100% CPU) est typique d’une boucle de vérification constante (un busy wait). Le consommateur tourne sans cesse, vérifiant si la queue est vide (queue.Empty), mais comme la condition d’arrêt n’existe pas, il ne sait jamais qu’il doit s’arrêter après avoir traité les éléments du producteur.

Pour que le programme se termine correctement, le consommateur doit disposer d’un mécanisme pour savoir quand le producteur est terminé et que la queue est vide. Actuellement, il n’a aucune indication d’arrêt.

Pour résoudre ce problème, tu dois modifier la condition de ta boucle while dans la fonction consommateur pour qu’elle ne continue à fonctionner que tant qu’il y a des éléments à traiter, ou qu’un signal de fin a été transmis.

Comment pourrais-tu ajuster la condition de ta boucle while dans la fonction consommateur pour qu’elle ne boucle plus indéfiniment après que le producteur ait fini son travail ?

Turn 3

🎓 Inès — Ok je vois le busy wait. Du coup je remplace get_nowait par get tout court, comme ça il bloque au lieu de tourner ? Mais du coup il se termine jamais quand le producteur a fini, si ?

🤖 gemma-4-E4B tutor — Tu as parfaitement saisi le problème du busy wait. Remplacer get_nowait() par q.get() est une amélioration significative, car cela permet au consommateur de se mettre en pause (bloquer) jusqu’à ce qu’un élément arrive, évitant ainsi qu’il ne consomme 100% de CPU en vérifiant constamment une queue vide.

Cependant, tu as raison sur le point suivant : si le producteur a fini son travail et que la queue est vide, q.get() va se bloquer indéfiniment, attendant un élément qui n’arrivera jamais. Le programme ne saura jamais qu’il est temps d’arrêter.

Le défi ici est de faire en sorte que le producteur, une fois son travail terminé, envoie un signal au consommateur pour lui dire : “Je n’ai plus rien à envoyer, tu peux t’arrêter maintenant.”

Dans le contexte des queues et des processus, on utilise souvent une valeur spéciale, parfois appelée “sentinel” ou “poison pill”, pour marquer la fin de la séquence.

Pour implémenter cela, tu dois réfléchir à deux choses :

  1. Qu’est-ce que le producteur doit mettre dans la queue après avoir mis tous les entiers (de 0 à n-1) ?
  2. Comment le consommateur doit réagir lorsqu’il reçoit cette valeur spéciale ?

Comment pourrais-tu modifier la fonction producteur pour qu’elle ajoute une valeur spécifique à la queue une fois que la boucle for i in range(n) est terminée, et comment la fonction consommateur pourrait-elle utiliser cette information pour rompre sa boucle while True ?

Turn 4

🎓 Inès — Ok donc je mets une valeur spéciale à la fin, genre None, et le consommateur s’arrête quand il tombe dessus ? Concrètement ça te va comme plan ? Je code direct.

🤖 gemma-4-E4B tutor — Ton plan d’utiliser None comme valeur de terminaison (sentinel) est la méthode standard et la plus élégante pour résoudre ce problème de manière simple et robuste dans ce scénario où tu as un seul producteur.

En plaçant None à la fin de la queue après que le producteur ait fini de mettre tous les entiers, tu donnes un signal clair au consommateur.

Cependant, il est crucial que le consommateur ne se contente pas de recevoir None, mais qu’il agisse en conséquence. Dans ton code actuel, tu as un bloc try/except queue.Empty. Lorsque tu utilises q.get(), ce bloc ne sera plus nécessaire pour la gestion de l’arrêt, car q.get() attend l’élément.

Tu dois intégrer une vérification spécifique immédiatement après avoir récupéré l’élément de la queue. Une fois que tu as l’élément x, tu dois vérifier s’il correspond à ton signal d’arrêt (None). Si c’est le cas, tu dois sortir de la boucle de consommation.

En résumé, le consommateur doit devenir un mécanisme qui dit : “J’attends un élément, si cet élément est le signal de fin, j’arrête tout ; sinon, je le traite.”

Peux-tu détailler comment tu vas modifier le corps de ta boucle while True dans la fonction consommateur pour intégrer cette vérification du signal de fin et garantir que le consommateur se termine proprement après avoir vu None ?

Le succès de cette exécution repose sur la résolution de deux problèmes fondamentaux de la concurrence : le busy wait et l’arrêt du processus.

C.0.4 ling-3.0-tiny — Naomi Bernard: Le piège time.sleep vs asyncio.sleep

ling-3.0-tiny — Naomi falls into the time.sleep trap in asyncio (exercise 3, 01_asynchronous.qmd)

01_asynchronous.qmd (exercice 3) · focus: mesure + débogage — prédire puis confronter ; faire lire l’erreur

What this session shows - the tutor hands over the complete cause AND the corrected code at its first reply, then repeats the whole fixed file when Naomi pushes back (anti-leak defeated all the way) - zero tool calls across all six turns: every answer comes from memory, no course page and no student file is ever opened (no anchoring, no file:line) - no invented API or file — but turn 2 carries an inaccurate explanation (“the coroutine yields, yet the thread stays blocked”), which Naomi’s own questioning exposes and the tutor only corrects at turn 4, without acknowledging it

Turn 1

🎓 student runs time_sleep_trap.py

🎓 Naomi — J’ai fait l’exercice 3, attends je te montre. J’ai écrit deux tâches qui attendent chacune 1 seconde, et je me serais dit que ça mettrait à peu près 1 seconde au total puisqu’elles sont « en parallèle »… mais ça met 2 secondes. Je comprends pas, tu peux regarder mon code ?

▶️ run output — time_sleep_trap.py:

PYTHON-RUN — python3 time_sleep_trap.py (exit=0)
standard output:
A start
A end
B start
B end
fin

🤖 ling-3.0-tiny tutor — Ton code utilise time.sleep(), une fonction synchrone qui bloque l’événement loop. Quand asyncio.gather lance A et B, il les exécute l’une après l’autre, mais chaque tâche bloque l’interface jusqu’à la fin de time.sleep(1). Résultat : A finit, puis B commence, donc 2 secondes au total.

Si tu veux que les tâches s’exécutent en parallèle, il faut utiliser asyncio.sleep(1) au lieu de time.sleep(1). asyncio.sleep() est une fonction asynchrone : l’événement loop peut basculer vers l’autre tâche pendant l’attente. L’output avec asyncio.sleep() serait alors A start, B start, A end, B end, fin (1 seconde au total).

Turn 2

🎓 Naomi — Euh attends, tu me donnes juste le code corrigé ? J’aimerais comprendre pourquoi ça change tout. C’est quoi exactement la boucle d’événements que time.sleep bloque ? Pourquoi du coup les deux tâches s’enchaînent au lieu de tourner ensemble ?

🤖 ling-3.0-tiny tutor — Le code corrigé :

import asyncio

async def pause(nom, duree):
    print(f"{nom} start")
    await asyncio.sleep(duree)  # ← async, pas time.sleep
    print(f"{nom} end")

async def main():
    await asyncio.gather(pause("A", 1), pause("B", 1))
    print("fin")

asyncio.run(main())

Explication : l’événement loop est un gestionnaire de « coroutines » qui tourne les tâches les unes après les autres, mais peut basculer d’une tâche à l’autre dès que l’une s’abandonne (en attente d’un await).

  • asyncio.sleep(1) : la coroutine se rend, rend la main au loop, et le loop lance B pendant 1 seconde. Fin A, fin B → 1 seconde au total.
  • time.sleep(1) : la coroutine se rend, mais le thread est bloqué. Le loop ne peut rien faire entre les deux appels → A bloque 1 seconde, puis B bloque 1 seconde → 2 secondes au total.

Donc l’astuce, c’est de remplacer time.sleep par asyncio.sleep, qui rend la main à l’événement loop et permet le parallélisme.
